# Deployment and release operations

## Four private repositories

Use `sanjuconnectrader/taskflow-web`, `taskflow-backend`, `taskflow-desktop`, and `taskflow-mobile`. Each corresponding local directory has its own Git history, dependency lockfile, README and workflow. Keep frontend and backend in separate directories.

Clone them beside each other as `frontend`, `backend`, `desktop`, and `mobile` for the default local asset scripts. Else set `FRONTEND_OUT` to the absolute frontend export directory before `npm run assets`.

Repository Settings → Actions must allow workflows. Set `main` as the default branch. Protect `main` with required CI checks and reviewed pull requests. Protect version tags from unreviewed creation/deletion. GitHub environment approval rules require separate repository/account configuration and may require a plan supporting protection on private repositories.

## Secrets and repository variables

Enter secrets in Settings → Secrets and variables → Actions. Add a `production` Environment in Settings → Environments with required reviewers, prevent self-review where supported, restrict deployment to `v*` tags, and place deployment/signing secrets there. Never place the local database password in tracked files.

| Repository | Actions secrets                                                                                                            | Repository variables                     |
| ---------- | -------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| Web        | `VERCEL_TOKEN`, `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID`                                                                       | `API_PUBLIC_URL=https://api.example.com` |
| Backend    | `CI_DB_PASSWORD` (separate disposable test password, URL-safe), `RENDER_API_KEY`, `RENDER_SERVICE_ID`                      | None required                            |
| Desktop    | `FRONTEND_READ_TOKEN`, optionally `WINDOWS_CSC_LINK`, `WINDOWS_CSC_KEY_PASSWORD`                                           | `API_PUBLIC_URL`, `FRONTEND_REF`         |
| Mobile     | `FRONTEND_READ_TOKEN`, `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD` | `API_PUBLIC_URL`, `FRONTEND_REF`         |

`FRONTEND_REF` must be the **40-character commit SHA** of a reviewed frontend version. Both native workflows reject unpinned references. `FRONTEND_READ_TOKEN` should be a fine-grained read-only token for the private web repository; a GitHub App installation token is preferable for larger teams. The current workflows accept a stored read token. They never use `pull_request_target` to run untrusted contributions with secrets.

`CI_DB_PASSWORD` is for a temporary Actions PostgreSQL service only; use a random URL-safe value. Fork pull requests do not receive secrets, so backend integration validation must run in an authorized branch context. Production `DATABASE_URL` belongs in Render's encrypted environment, not the web/native workflows. No `SESSION_SECRET` is needed: sessions are opaque random tokens and only their hashes are stored, rather than signed client-side claims.

For local Android credentials generated by `init-signing.mjs`, upload the key bytes as base64 to `ANDROID_KEYSTORE_BASE64`, and upload each `.env.signing` value to its matching secret. Avoid printing either the base64 or passwords. Example in PowerShell after `gh auth login`:

```powershell
cd mobile
$keyBytes = [System.IO.File]::ReadAllBytes((Resolve-Path '.signing/taskflow-release.jks'))
[Convert]::ToBase64String($keyBytes) | gh secret set ANDROID_KEYSTORE_BASE64 --repo sanjuconnectrader/taskflow-mobile --env production
Get-Content .env.signing | ForEach-Object {
  $parts = $_ -split '=', 2
  if ($parts[0] -ne 'ANDROID_KEYSTORE_PATH' -and $parts.Length -eq 2) {
    $parts[1] | gh secret set $parts[0] --repo sanjuconnectrader/taskflow-mobile --env production
  }
}
```

Do not use a public testing key for distributed updates. Store a recovery copy of your release key in your organization's credential vault. Credentials are not supplied in the source.

## Backend on Render

1. Provision managed PostgreSQL and copy its TLS-validated connection URL into Render's `DATABASE_URL`. Use a dedicated application database role and back up the database.
2. Create a Render Blueprint from the private backend repository using `render.yaml`, or create an equivalent Node service. Grant Render access only to that repository. Blueprint resources may incur provider charges; choose the plan yourself.
3. Set `NODE_ENV=production`, `API_PUBLIC_URL=https://api.example.com`, `APP_WEB_ORIGIN=https://app.example.com`, and `CORS_ALLOWED_ORIGINS=https://app.example.com,taskflow://app,https://localhost`. Include `http://localhost` only if an explicitly required native platform uses it; never use wildcard origins with credentials.
4. Keep `COOKIE_SAME_SITE=lax` for same-site custom domains. Use `none` only for a deliberate cross-site setup with Secure cookies and browser compatibility testing.
5. Set private object-storage variables from `.env.example`. Use least-privilege bucket credentials. Configure the bucket's CORS to permit `PUT` from your exact web/native origins with `Content-Type`; do not allow public reads. Configure lifecycle cleanup for abandoned unconfirmed uploads.
6. Build command: `npm ci && npm run build`. Pre-deploy: `npm run db:migrate`. Start: `npm start`. Health path: `/health`. Do not run seeds.
7. Disable provider auto-deploys; the tag workflow deploys **the validated commit SHA** using Render's API after the `production` environment gate. Copy the Render service ID and API key into GitHub's production secrets. The workflow polls and fails on a failed deployment.
8. Configure the reminder cron job against the same database. Its schedule uses UTC dates, is idempotent per task/user/day, and respects reminder preferences. It writes notifications; clients discover them on polling/refetch. It is not a native push service. Scale to one API instance initially; a Socket.IO Redis adapter and distributed limiter are required for multi-instance consistency.
9. Verify `/health`, register a real account, and test web/native CORS and authorization before distributing native releases.

## Web on Vercel

1. Create a Vercel project for `taskflow-web`, framework Next.js. The checked-in config exports to `out`.
2. Set `NEXT_PUBLIC_API_URL=https://api.example.com` in Vercel Production and Preview environments and set matching GitHub repository variable `API_PUBLIC_URL`. These are public addresses, not secrets.
3. Connect your custom `app.example.com` domain and configure the API domain first. Keep both under the same registrable domain for cookies.
4. Set the Vercel token, organization ID and project ID in GitHub production secrets.
5. To enforce tag-only production, disable Vercel's independent Git-triggered production deployments (disconnect its Git integration after project setup if necessary). Otherwise pushes could deploy outside GitHub's production approval gate.
6. Push a reviewed `v1.0.0` tag whose version matches `package.json`. The workflow installs from the lockfile, type-checks, tests, audits production dependencies, and builds. After approval it runs the pinned Vercel CLI pull → build → deploy --prebuilt sequence.

## Native releases

1. Deploy and verify the shared backend and web release first.
2. Set the same HTTPS `API_PUBLIC_URL` in desktop and mobile repository variables. Set `FRONTEND_REF` to the exact verified web commit SHA. The UI is compiled and bundled locally into each native package.
3. Set each native `package.json` version, commit it, and create a matching `vX.Y.Z` tag. Android derives version code as `major*10000+minor*100+patch` (minor and patch ≤99); always increase it for updates. Do not reuse a previously published version code.
4. The Windows workflow runs on Windows, tests the shell and shared frontend, builds the UI, checks Electron startup, then creates an NSIS installer. Optional signing credentials sign it; without them the installer remains unsigned. The `.exe` is uploaded as a workflow artifact and to the tag's GitHub Release.
5. Android runs on Ubuntu with Node 22, JDK 21, SDK 36, and restored signing secrets. It builds the shared UI, syncs Capacitor, signs `assembleRelease`, verifies the APK signature and uploads the APK to GitHub Releases. The temporary keystore is removed after the job. Back up the original key independently.
6. Repositories are private; their Releases require access to the repository. To distribute publicly, use a separate approved distribution channel or change visibility deliberately.
7. Install and test each downloaded artifact on the target OS/device. Verify login, workspace switching, task CRUD, comments, startup persistence, expiration, logout, back navigation and network failure. A generated installer/APK does not establish that these device flows passed.

## Tag procedure

```powershell
# In EACH repository, after its package version and reviewed changes are committed:
git switch main
git pull --ff-only
git tag -a v1.0.0 -m "TaskFlow 1.0.0"
git push origin v1.0.0
```

Approve the `production` environment deployment after validation succeeds. Do not tag before secrets/variables and required reviewers are configured. Do not move a published tag; issue a new patch version. Build artifacts and publishing are intentionally triggered by version tags; ordinary pushes and PRs validate without production deployment.

## Rollback and updates

Use Vercel's previous successful deployment or re-deploy a known-good web version. On Render, deploy a known-good commit explicitly. Keep database migrations backward-compatible (expand then contract); restoring application code does not undo schema changes. Back up before a destructive migration. For native apps, issue a new version embedding a reviewed older frontend commit if necessary; Android updates must use the same key and higher version code. There is no automatic desktop updater in this release.

## Operator-assisted account recovery

The public recovery request always returns the same response. Eligible requests appear in Settings → Recovery. Workspace administrators can only handle ordinary members/viewers who own or administer no other workspace. Since public registration creates a personal workspace owned by that user, most self-registered users require platform-operator assistance. This is an intentional restriction preventing an unrelated workspace administrator from taking over an account with ownership privileges elsewhere.

A trusted deployment operator may provision an existing account with `BOOTSTRAP_ADMIN_EMAIL=<email>` and `CONFIRM_OPERATOR_BOOTSTRAP=yes` followed by `npm run admin:bootstrap`. Do this only in a protected operator shell. Public registration never assigns this role. Operators independently verify sole-owner identity, record verification notes and approve an eligible request. Deliver the one-time reset authorization through the verified private support channel; it is shown once, stored only as a hash, expires in 15 minutes, and cannot be reused. Reset revokes all account sessions.

Platform operator recovery is deliberately not exposed through these HTTP endpoints. Use your organization's separately controlled break-glass process with two-person verification and database/operator audit, then revoke sessions. There is no master password or email OTP. Record and monitor recovery audit events; define the organization-specific identity proof and retention policy before public launch.
